# Achievement System Audit — Training Platform

Дата: 14 октября 2026. Аудит актуальной ветки `feature/roadmap-react`, включая незакоммиченные результаты задач 7–9. Это проект архитектуры, не реализация.

Создан только этот отчёт. Код, модели, миграции, тесты и React не изменялись; Django и команды восстановления не запускались, подключения к базам не выполнялись. Сведения о данных получены из исходников, миграций, существующих тестов и документации. Фактическая полнота исторических записей production не проверялась. Ниже явно разделены существующие факты и предлагаемые правила.

Главный вывод: надёжные положительные доказательства уже есть для нескольких базовых наград. Доказательств отсутствия ошибок за всю историю недостаточно для идеального прохождения Sandbox и полной «Чистой недели». Текущий нулевой счётчик или последнее approved не заменяют полную историю.

## 1. Матрица достижений

Обозначения: **доступно** — исходные положительные доказательства есть, можно реализовать автоматический evaluator без нового предметного источника; **условно** — нужен строгий отбор записей и согласование политики/доверия к источнику; **ожидает источник** — необходимых фактов нет или их история недостаточна. Во всех случаях самого backend наград пока нет.

Коды ниже предлагаются как стабильные, не зависят от номера станции. Редкость дополнительных наград, кроме указанной пользователем «Чистой недели», пока не утверждена.

| Линейка / достижение | Уровень и точное условие | Существующее доказательство | Готовность |
|---|---|---|---|
| `training_program` | Бронза: обучение подтверждено завершённым | Последний `TrainingConfirmationEvent.action=confirmed` для конкретной адаптации; staff-сервис подтверждения [S1] | Доступно для применимой программы, источник manual; это не импорт Teachbase |
| ↳ | Серебро: ≤11 учебных рабочих дней **и** результат **>90%** | Нет фактического datetime старта, балла и даты прохождения курса [S1, S8] | Ожидает источник |
| ↳ | Золото: ≤6 учебных рабочих дней **и** результат **>95%** | Те же отсутствующие данные | Ожидает источник |
| ↳ | Платина: ≤6 учебных рабочих дней **и** результат **ровно 100%** | Те же отсутствующие данные; округление до 100 не подходит | Ожидает источник |
| `sandbox_program` | Бронза: весь обязательный набор технически завершён | `SandboxProgramCompletion` и его frozen snapshot; не `status=passed` [S2, S3] | Доступно, включая доказанно восстановленный legacy-снимок |

| ↳ | Золото: техническое завершение + все обязательные клиентские ответы приняты + ≤2 рестартов + ≤2 возвратов | Последнее approved есть, полного числа возвратов и frozen обязательности ответа нет [S2, S4, S7] | Ожидает источник |

| `review_quality` | Бронза ≥80%; серебро ≥90%; золото **>95%** | `WeeklyMetric.quality_percent` и история этапов; итоговые поля отдельно [S8–S10] | Условно: для датированных однозначно относящихся к WITH_REVIEW измерений по правилу раздела 3 |
| `independent_speed` | Бронза ≥5; серебро ≥7; золото ≥9; платина **>10 т/ч** | `WeeklyMetric.speed_hours` — Decimal, несмотря на название это тикеты/час; период и история [S8, S9] | Условно: только NO_REVIEW, без какого-либо условия качества |
| `probation_new_hire` | Бронза >60; серебро 46–60; золото 31–45; платина ≤30 календарных дней, только успешный NEW_HIRE | `probation_start_date`, `completed_at`, `completion_status`, `completed_by`, финальный этап [S8, S11] | Доступно после проверки целостности и согласования включения первого дня |
| `sandbox_first_success` — «Первый запуск» | ≥1 отдельного технически успешного зачётного задания; фиксированная редкость не утверждена | `get_technical_evidence()` для attempt_number=1; либо доказательство из frozen snapshot [S2–S4] | Доступно; название не означает запуск контейнера |
| `sandbox_five_successes` — «Пять из пяти» | ≥5 **разных** технически успешных заданий; фиксированная редкость не утверждена | Те же источники, distinct task_id, без тренировок [S2–S4] | Доступно в доказанном составе программы |
| `sandbox_first_five_clean_answers` — «Без замечаний» | Первые пять разных клиентских ответов приняты без доработок; фиксированная редкость не утверждена | Не хватает полного порядка отправок и решений [S7] | Ожидает источник |
| `review_quality_streak` — «Стабильность — признак мастерства» | Три последовательные недельные метрики ≥90% на этапе проверок; фиксированная редкость не утверждена | `week_number`, nullable `week_start_date`, качество, StageHistory [S8, S9] | Условно при достоверных трёх законченных соседних периодах; одного подряд идущего week_number недостаточно |
| `independent_engineer` — «Самостоятельный инженер» | Подтверждённый переход в NO_REVIEW; фиксированная редкость не утверждена | Реальный переход `StageHistory` с автором следующей записи [S8, S12] | Условно. Рекомендуемый v1 — штатный OPTIONAL_REVIEW → NO_REVIEW; правило пропуска требует согласования |
| `clean_week` — «Чистая неделя» | **Отдельная секретная фиксированная платина**: 100% по итогам полной рабочей недели WITH_REVIEW | Нет подтверждения полноты недели, периода фактического измерения, объёма проверки [S8–S10] | Ожидает источник |
| Будущие награды за тесты / практику | Условия и редкость не утверждены | Assessment имеет результаты тестов; Sandbox — бинарный технический зачёт, не балл курса [S13] | Не запускать до утверждения условий и контекста |

Получится **11 определений**: пять основных линеек и шесть дополнительных, включая clean_week. У основной линейки качества только три уровня; отдельную секретную платину нельзя превращать в её четвёртый уровень. У других основных линеек — четыре уровня.

Для внутреннего перевода нельзя выдавать обучение/Sandbox за `not_required`: это не completed. Политика применимости должна задаваться для определения и контекста программы. Скорость/качество рабочих этапов применимы обоим типам входа. Линейка выхода ИС — только NEW_HIRE. Для дополнительных Sandbox-наград надо отдельно утвердить, считается ли добровольная программа внутреннего сотрудника; сам факт неприменимости никогда не даёт награду. Это следует из `build_roadmap()`/`REQUIREMENTS_V1`, не из номера станции [S12].

## 2. Точные источники и ограничения фактов

### 2.1. Обучение

В [roadmap/models.py](roadmap/models.py), `TrainingConfirmationEvent` хранит journey, stage_code, action, actor, created_at и comment. В [roadmap/services/confirmations.py](roadmap/services/confirmations.py), `change_training_confirmation()` проверяет staff, блокирует строку TraineeJourney, сохраняет confirmed/revoked и не создаёт дубль уже действующего состояния. Отзыв — новое событие. [S1]

`created_at` — время регистрации решения наставника. Это не подтверждённая дата фактического завершения курса. Ни оценки, ни datetime старта обучения, ни идентификатора курса/provider result там нет. `TraineeJourney.stage_started_at` и `StageHistory.started_at` — даты адаптационного этапа, допускающие ручное указание; в legacy общего training-program может не быть. Их нельзя объявлять точным стартом Teachbase. `TraineeStage.min_days/max_days` — план, не доказательство фактического обучения. [S1, S8, S12]

После задачи 9 [roadmap/services/actions.py](roadmap/services/actions.py), `training_destination()` проверяет только конфигурацию перехода Teachbase. `ROADMAP_TEACHBASE_URL`/allowed hosts не являются интеграцией результатов. Подтверждение manual позволяет бронзу, но не позволяет выдумать срок или 100%.

Предлагаемый заменяемый источник — нормализованный `CourseCompletionEvidence`: stable program/course identity, participant, adaptation/context, фактические started_at/completed_at, Decimal score_percent, provider, provider_event_id, provider_revision, recorded_at, подтверждение первого неполного дня, версия календарной политики и provenance. Сначала manual adapter даёт только completion=true с отсутствующими score/start; позднее Teachbase/import или собственный course adapter заполняет реальные факты. Отсутствующее поле остаётся unknown, не превращается в ноль или дату ИС. Вручную выданный трофей должен обозначаться ручным, а не получать поддельные «баллы Teachbase».

### 2.2. Sandbox: что реально хранится

| Вопрос аудита | Факт по коду | Следствие для наград |
|---|---|---|
| Что такое restart? | `run_environment_restart()` удаляет старые task/terminal контейнеры, создаёт новые, ждёт готовности, затем увеличивает restart_count и сохраняет результат. Это **пересоздание окружения**, не Docker restart того же контейнера и не запуск check.sh [S6] | Считать успешные сбросы окружения; термин «перезапуск» зафиксировать в правилах |
| Когда увеличивается счётчик? | После создания и ожидания готовности, перед attempt.save. `mark_environment_restart_error()` не увеличивает счётчик [S6] | Ошибка запроса/очереди/создания не равна одному успешно сохранённому рестарту |
| Есть ли история рестартов? | Есть агрегат restart_count и application log. Модели журнала операций нет [S4, S6] | Нельзя получить все даты/авторов/причины рестартов и доказать полноту по логам с неизвестным retention |
| Есть ли все запуски проверки? | После возвращённого exit_code создаётся CheckRun: success в atomic, failure отдельно. Docker exception, background exception, watchdog меняют текущие поля без CheckRun [S5, S15] | Есть история завершённых зафиксированных результатов, а не полный журнал всех запланированных/реальных запусков; сбой cleanup/сохранения после возврата checker тоже может оставить пробел |
| Что означает attempts_count? | Увеличивается при маркировке RUNNING перед постановкой в Celery; `try_mark_attempt_check_running()` использует F + guard [S5] | Это число принятых запусков на этом пути, не число отказов и не гарантия того, что check.sh исполнился столько раз |
| Можно найти первую проверку? | Первую **сохранённую** по `(created_at, pk)` найти можно. CheckRun.created_at — регистрация результата, нет стартового ordinal/job ID [S4, S5] | Нельзя приравнять её к первой когда-либо выполненной проверке, особенно до миграции 0017 или после сбоя |
| Сохраняются ли возвраты ответа? | `save_mentor_feedback()` перезаписывает decision/actor/time/feedback; счётчика и журнала возвратов нет [S7] | Текущее approved не доказывает zero revisions |
| Сохраняются ли отправки? | `check_task()` сохраняет текущие тексты; при отправке сбрасывает decision/reviewer/date в not_reviewed/NULL. Отдельного submission/version нет [S7] | Нельзя достоверно установить first submission и его результат |
| Помогает ли AIReview? | При непустом task.ai_review_context `create_ai_review()` сохраняет копию client_answer/context. Последнее решение записывается в последнюю AIReview с совпадающим текстом [S7] | Полезный частичный снимок, но не канонический журнал отправок/отзывов; AI optional, review решение тоже изменяется |
| Что происходит с датами? | started_at перезаписывается при старте/рестарте; finished_at меняется при техническом успехе, отправке/решении/доработке; technical_passed_at — отдельное доказательство [S4–S7] | Не использовать finished_at как техническое завершение, started_at как неизменный первый старт |
| Влияют ли тренировки? | attempt_number>1, отдельные строки/счётчики; `rerun_task()` создаёт следующую попытку, исходная остаётся; технический агрегатор использует №1 [S3, S4, S7] | Исключить тренировки из обязательного зачёта, рестартов и идеальности исходного прохода |
| Можно доказать идеальное прохождение всех заданий? | Нет обязательной полной истории отправок, всех решений, запусков и coverage marker [S4–S7] | Автоматическая платина на старой модели небезопасна |

`check_task_container()` обычно выполняет `/task/check.sh` через timeout. Для одного WordPress-сценария он выполняет серверный PHP checker вместо локального скрипта. Exit 124 записывается как FAILED с текстом таймаута, а не отдельный тип инфраструктурного результата. Поэтому журнал для наград должен описывать **техническую проверку**, не предполагать единственный физический check.sh и не читать «ошибка стажёра» из любого nonzero exit без утверждённой политики. [sandbox/services/docker_service.py](sandbox/services/docker_service.py), `check_task_container()`, строки 132–171; [S5].

В 15 `training_tasks/l1/*/task.json` репозитория сейчас manual review и AI context включены. Это проверка файлов, не состояния базы и не доказательство покрытия исторических отправок. Task.ai_review_context допускает пустой dict; тест `test_check_task_does_not_create_ai_review_without_context` подтверждает этот путь. [S7, S16]

### 2.3. Надёжный технический результат и legacy

Источником положительного зачёта остаётся [sandbox/services/technical_evidence.py](sandbox/services/technical_evidence.py), `get_technical_evidence()`/`credit_task_completed()`:

1. technical_passed_at — первичное доказательство.
2. При его отсутствии — CheckRun той же зачётной попытки с result=passed **и** exit_code=0; берётся первый такой сохранённый успех.
3. status=passed, check_status=passed или approved наставника сами по себе не дают технический успех.
4. Противоречивые результаты диагностируются; дата технического успеха не отменяется последующей доработкой. [S3]

Для основной бронзы использовать `SandboxProgramCompletion`, а не пересчитать текущий каталог. Снимок хранит task_id, attempt_id, task_slug, order, evidence_source, passed_at, check_run_id и fingerprint состава. Состав/дата сохраняются при удалении/деактивации заданий и очереди. В него **не входят** рестарты, failures, требование ответа, история отправок, решения наставников или версия содержимого checker. [S2]

Высшие уровни должны проверять **тот же frozen набор**, иначе добавление/удаление заданий изменит условие уже пройденной программы. Сегодня требуется восстановить связанные credit attempts по snapshot IDs и проверить user/task/attempt_number. Если Task/TaskAttempt/CheckRun удалены, их FK CASCADE уничтожает детальные факты, хотя JSON снимок завершения остаётся; пропавшие counters/reviews нельзя считать нулями. Task.requires_manual_review изменяется через admin, в snapshot этот флаг не зафиксирован. Следовательно, для оценки всех ответов нужен отдельный frozen requirement/evidence snapshot новой версии. Старый SandboxProgramCompletion не переписывать. [S2, S4, sandbox/admin.py — enable/disable_manual_review]

Миграции 0017 CheckRun и 0022 technical_passed_at добавляют структуру, не восстанавливают все прошлые проверки. Миграция 0031 SandboxProgramCompletion тоже не создаёт legacy-награды или завершения. `restore_program_completion()`/команда restore используют реальные технические доказательства, актуальный на восстановление состав и fingerprint guard. Восстановленный снимок с source=legacy_restore достаточен для **технической бронзы**, но не превращает историю в идеальный проход. Он не доказывает, что состав совпадал с программой много месяцев назад. [S2, S14]

## 3. Что можно автоматизировать сейчас

Предлагаемый минимальный первый выпуск:

- `training_program` bronze из действующего ручного события confirmed, с явным source=manual и проверкой применимости.
- `sandbox_program` bronze из сохранённого completion.
- `sandbox_first_success` и `sandbox_five_successes`: distinct технические результаты attempt_number=1; завершённый frozen snapshot также доказывает нужное число заданий. Не использовать is_current: после тренировки зачётная попытка может быть исторической.
- `probation_new_hire`: максимальный подходящий уровень из подтверждённого successful outcome и календарной длительности.
- При согласовании строгого правила — основное качество/скорость и вход в NO_REVIEW только для однозначных записей.

Эти пункты доступны **по структуре данных**; массовую пригодность production-истории надо проверять отдельно. Если источника/автора/даты не хватает, вернуть eligibility=unknown/evidence_missing, не fabricated completed и не процент из отсутствующих значений. [S1–S4, S8, S11, S12]

### Проверяемое правило качества и скорости на существующих полях

Предложение для conservative v1, без изменения существующих readiness:

1. Брать WeeklyMetric с реальным сохранённым week_start_date и ненулевой полнотой **данных**, а не требованием положительного числового значения: само значение может законно быть 0. Отсутствующее quality/speed — unknown.
2. Использовать текущую интерпретацию периода дневника `[week_start_date, week_start_date + 7 дней)`. Она следует из save_weekly_metric(), но не означает ISO-неделю и не доказывает фактическую посещаемость.
3. Для исторической автоматизации выбирать законченный период; требовать непротиворечивую StageHistory, покрывающую весь период одной непрерывной применимой группой. Для наиболее строгого v1 — одним посещением StageHistory, без внутрипериодного перехода, возврата, наложения или пробела.
4. Quality evaluator принимает только группу WITH_REVIEW; speed evaluator — только NO_REVIEW. Не брать метрику предыдущего этапа потому, что текущая карточка уже на новом этапе.
5. Без сохранённой даты не пользоваться fallback «текущий этап» из UI `_get_stage_for_date()`. Он нужен отображению старых данных, а не доказательству награды. Даже при точной дате этот helper смотрит одну дату, не весь интервал.
6. Считать записанный weekly показатель авторитетным агрегатом соответствующего периода по согласованной политике. Это допущение о семантике ввода; количество измерений/проверок сейчас неизвестно. При требовании доказать наблюдение за всеми рабочими днями нужны новые поля из раздела 5.
7. Делать snapshot исходных значений, period, StageHistory IDs и source digest в событии награды. Не заменять этим snapshot сам WeeklyMetric.

Это позволяет ограниченную автоматизацию главных порогов на однозначных данных, но не «Чистую неделю»: для неё нужна фактическая полнота наблюдения, не только отсутствие перехода. Правило должно быть согласовано прежде, чем запустить backfill. Источники: [S8, S9].

### Недельное и итоговое качество, возвраты

`fixed_quality_percent` + `quality_fixed_at` — текущая итоговая фиксация на карточке. `_apply_quality_stage_transition()` берёт последнее ненулевое quality_percent **по week_number**, без фильтра этапа/периода/посещения. При возврате на WITH_REVIEW оба поля очищаются. При следующем выходе может повторно попасть старая недельная запись, если новой нет. Поэтому фиксация сама по себе не доказывает новое измерение текущего посещения. [S8, S10]

Награду основного качества рекомендовано выдавать по проверенной WeeklyMetric, а не по «любому fixed_quality_percent». Если продукт выберет именно **итоговое** качество, evaluator должен сопоставить зафиксированное значение с доказанной метрикой/посещением и событием фиксации; без этого итоговый режим ждать улучшения источника. Нужно согласовать «по лучшей подтверждённой неделе» против «по итоговому результату» — сейчас задача задаёт числовые пороги, но не это различие.

Возврат не снимает ранее честно полученную награду. Новое повышение требует нового валидного доказательства либо ещё не обработанного прежнего валидного результата. Данные разных посещений нельзя выдавать за три непрерывные недели одного посещения. Будущая история фиксаций должна сохранять прошлые значения, которые текущая карточка очищает. [S10]

Для скорости не добавлять ни fixed_quality_percent, ни quality_required, ни финальное качество. Даже если в строке WeeklyMetric осталось старое quality_percent, оно не участвует в speed rule. Формы уже исключают редактирование качества вне WITH_REVIEW; это подтверждает, что старое ненулевое качество может оставаться в строках и не является измерением текущего этапа. [S9, S10]

## 4. Для каких наград не хватает данных

| Недостающий факт | Почему текущие поля недостаточны | Что блокирует |
|---|---|---|
| Фактический старт/финиш обучения и итоговый процент | Event.created_at и даты адаптации отражают учёт; score отсутствует | Training silver/gold/platinum |
| История успешно завершённых и неудачных рестартов с coverage | Агрегат mutable; ошибки не увеличивают его, нет операции/автора | Безоговорочный sandbox silver и аудит технической идеальности |
| Все запуски/результаты технической проверки | CheckRun нет для ERROR/watchdog; counts отражают планирование, старые проверки могли предшествовать 0017 | Sandbox platinum |
| Immutable версии отправок и решения по каждой версии | TaskAttempt перезаписывается; AIReview optional и решения меняются | Sandbox gold/platinum, «Без замечаний» |
| Frozen обязательность ответов/версия требований программы | Snapshot хранит IDs, но не requires_manual_review и не содержание | Все ответы приняты для исторического состава |
| Фактический период измерения, финальность, полнота рабочих дней/объём выборки | week_start_date nullable, interval end и coverage отсутствуют | «Чистая неделя», надёжная последовательность недель |

| Подтверждённый автор старого завершения/перехода | completed_by/changed_by nullable и SET_NULL | Автоматическая выдача на неоднозначном legacy |

Пропуск новой миграции учёта в прошлом нельзя замаскировать initial counter=0. Для повышенных уровней отсутствие ошибки может означать потерю истории. [S1–S12]

## 5. Какие события и поля нужны

Все названия в этом разделе — предложения, этих моделей сейчас нет.

### Sandbox

1. `SandboxEnvironmentEvent`: operation_id/UUID, attempt, credit/practice context, requested_by, requested_at, completed_at, kind=start/reset, origin=trainee/maintenance, outcome=success/error/unknown. Отдельно зафиксировать, входят ли административные восстановления в ограничение ≤2; рекомендуется считать trainee successful reset, системные ремонты — отдельно.
2. Дополнение/отдельный `TechnicalCheckExecution`: run_id, attempt, monotonic check_ordinal, request/start/finish timestamps, job/idempotency key, technical result, failure_class=technical/infrastructure/timeout, link на CheckRun. Ordinal выдаётся **до** запуска, а не выводится из завершённых CheckRun. Отдельно знать, стартовало ли исполнение checker.
3. `SandboxAnswerSubmission`: attempt, submission_ordinal, submitted_at, immutable client_answer/internal_report snapshot и digest. Только валидная отправка, не сохранение черновика. Изменение черновика до первой отправки не считается доработкой наставника. Сохранённые отправленные версии не заменяются новым текстом.
4. `SandboxAnswerReviewEvent`: submission, actor, occurred_at/recorded_at, approved/needs_revision/comment/correction, стабильный ID операции, при необходимости supersedes. Решение обязательно связывается с конкретной версией ответа.
5. Coverage/provenance: зафиксированная версия учёта на **новой** зачётной попытке и frozen наборе требований; для старых unknown. Требуется доказать учёт с начала предметного процесса. Включение журнала посередине старой попытки не делает её полной.
6. Отдельный frozen evidence/requirement manifest для наград: состав исходной программы, обязательность текста на каждом task, источник/версия условий. Существующий SandboxProgramCompletion сохранить неизменным. Для новых программ дополнять независимый versioned manifest, а не переписывать уже имеющиеся snapshots.

Не нужно логировать каждый keystroke ради first submission: достаточно всех отправленных версий и связанных решений. Если требуется аудит всех черновиков, это отдельное требование объёма/retention. Исходный код потери черновиков и отправок: `check_task()`/`save_mentor_feedback()` [S7].

### Метрики и обучение

Для `WeeklyMetric` или отдельного `WeeklyMetricRevision` нужны period_start/period_end, recorded_at/recorded_by, revision ID, state=draft/final, measured_at/finalized_at, ссылка/проверенная привязка к посещению StageHistory и признак коррекции прежней ревизии. Для полной недели — **подтверждение фактического покрытия** рабочих дней, например covered_workdays и полная выборка assessed_ticket_count; не вводить произвольный минимум ticket_count без утверждения продукта. База должна отличать full_week=true от «в строке написано 100».

Полный календарный интервал на WITH_REVIEW ещё не доказывает наблюдение за всю неделю: сотрудник мог работать не все дни, качество могло быть введено по одному проверенному тикету. Новый coverage marker должен иметь реальное основание, а не default=True для существующих данных. Поля недели и исправления отсутствуют в WeeklyMetric [S8, S9].

Для итогового качества — сохранять immutable факт фиксации с metric_revision_id, visit_id, actor/date/value, включая сброс текущей карточки при возврате. Для обучения — CourseCompletionEvidence из раздела 2.1. Дополнительные результаты тестов могут использовать AssessmentResult только после привязки к утверждённой учебной программе; практические баллы Sandbox сейчас отсутствуют. [S10, S13]

## 6. Как считать рестарты и доработки Sandbox

Предлагаемая семантика для утверждения:

- **Restart** — одно успешно завершённое пересоздание учебного окружения зачётной попытки. Повторный HTTP-запрос, duplicate Celery delivery, создание тренировочной попытки и повторный check не равны restart. Failed infrastructure reset не штрафует автоматически; его причина фиксируется.
- Серебро: сумма именно этих операций ≤2 по **всем обязательным зачётным попыткам frozen программы**. Техническое завершение должно быть сохранено. До полноценного журнала возможно только ограниченное доверенное использование restart_count с описанными оговорками; не суммировать текущие тренировочные attempts.
- **Возврат** — первое действительное needs_revision для конкретной отправленной версии. Повторное сохранение того же решения/правка комментария не создаёт второй возврат. После новой отправки следующая реальная needs_revision — новый возврат. Исправление ошибочного решения — отдельное correction, не удаление истории.
- Золото: все обязательные текстовые ответы approved, restart_total≤2, revision_total≤2, полная подтверждённая история. Состояние текущего активного каталога не подменяет frozen требования.
- Платина: для каждого обязательного task первый **достоверно учтённый с начала** технический execution успешно завершён, и первая submission получила approved без действительного needs_revision; весь набор проверен. Не выводить первое выполнение из attempt_number=1: внутри этой попытки могут быть многократные проверки.

Для платины пользователь не задал отдельное ограничение рестартов. Его нельзя молча добавить: first technical success и first answer acceptance — явные условия. Если платина должна всегда быть строже золота и включать zero/≤2 resets, нужно отдельное согласование. Например, три resets до первого check с последующим первым passed соответствуют буквальному условию платины, но не серебру/золоту. Evaluator должен проверять условия уровней независимо и брать максимальный подходящий, а не требовать предварительную серебряную выдачу.

Также надо согласовать судьбу timeout/infrastructure error до первого технического успеха: считать ли его проваленной первой попыткой либо unknown для ручного разбора. Текущая модель различает Docker ERROR и recorded timeout FAILED, но не хранит все такие случаи [S5, S15]. Без решения и coverage платину не выдавать.

Для «Без замечаний» предлагается выбрать первые пять **разных** зачётных client submissions по `(submitted_at, submission_id)`, а не любые пять последних approved. Повторная отправка одного задания не заменяет неудачный первый ответ другим успешным. Если продукт имел в виду первые пять task по order, это другая политика — порядок должен браться из frozen manifest, не изменяемого Task.order. [S2, S7]

## 7. Учебные и календарные дни

### Учебные

Предложение: локальные даты реальных study_started_at/study_completed_at в зафиксированной timezone программы; считать дни Пн–Пт включительно, затем исключить **только подтверждённый** первый неполный рабочий день при разрешённой версии политики. Стартовую и финальную границы не брать из probation_start_date.

Нужны согласования: что считается неполным первым днём (фиксированный cutoff либо явно подтверждённый effective start); учитываются ли отпуск/паузы обучения; как обрабатывается завершение в выходной. Пока задано исключение только субботы/воскресенья: государственные праздники и паузы не исключать молча. Последний неполный день отдельно исключать задача не просит. Не считать любой старт после полуночи «неполным»: обычный старт рабочего дня также позже 00:00.

Без подтверждённого фактического старта и правила первого дня timed tiers остаются unknown. Нельзя выбрать выгодную дату из нескольких legacy-этапов Teachbase. Источники отсутствия timestamp: `TrainingConfirmationEvent` и `TraineeJourney` [S1, S8].

### Календарные дни ИС

Рекомендуемая политика для «не позднее 30-го дня»: день probation_start_date — день 1, `day_number = (completed_at - probation_start_date).days + 1`. Утвердить до реализации. Текущая `TraineeJourney.days_total` использует разность без +1 и нулевой минимум, поэтому её нельзя незаметно применить к новой шкале «31–45-го дня». [S8, S11]

Используются реальные DateField, включая выходные; 90-дневный план NEW_HIRE и 30-дневный норматив INTERNAL_TRANSFER не заменяют фактическую длительность. INTERNAL_TRANSFER из линейки исключён. Проверять success, финальный этап, допустимые даты и подтверждение; DONE/progress=100/истечение времени не дают успех. В Roadmap `_probation()` уже отделяет terminated и incomplete исторический результат; эту логику не дублировать клиентским индексом станции. [S11, S12]

Проверочные границы будущих тестов: day 30/31, 45/46, 60/61; weekend, leap day; старт и финиш в один день; неверные/будущие даты. Для баллов курса — 90/90.01, 95/95.01, 99.99/100. Текущий WeeklyMetric.quality_percent — целое число, поэтому граница его золота 95/96, диапазон золота 96–100. Для скорости — 5/7/9/10/10.1. Использовать Decimal и реальные точные значения, а не округление UI.

## 8. Хранение уровней и истории

Все модели ниже предлагаются для будущего приложения `achievements`, не создаются этим аудитом.

| Модель | Минимальное назначение / поля |
|---|---|
| `AchievementDefinition` | immutable code, public UUID, title/description, category, secret, kind=tiered/fixed, active, applicability/source policy, evaluator_key, rule_version, безопасный art_key. Код не равен номеру станции. |
| `AchievementTier` | FK definition, stable tier code, rank, rarity bronze/silver/gold/platinum, описание условия, проверяемые parameters, версия правил. Unique(definition, tier_code/rank). Одна общая таблица уровней, не четыре таблицы. У качества три записи, у fixed секрета одна. |
| `UserAchievement` | Unique(user, definition), active highest earned tier либо NULL, state, first_granted_at, last_changed_at, revision/автоматический блок после отзыва. Не хранить вторую копию Roadmap current_stage или метрик. |
| `AchievementEvent` | append-only grant/upgrade/revoke, entitlement, from_tier/to_tier, actor nullable только для trusted automatic, occurred_at/recorded_at, source_type/provider/evidence ref, rule_version, source revision, evidence snapshot/digest, reason/comment, idempotency key, revoked event reference при отзыве. |
| `AchievementSourceEvent` / outbox | Durable нормализованное событие источника, provider+event_id unique, schema/version, user/context, payload/ref, created_at, processing status/retry/error. Можно объединить incoming-event и outbox в одну инфраструктурную таблицу. |

Максимальный уровень — одна активная запись на user/definition. Если впервые доказана платина, сохранить **один grant NULL→platinum**. Не создавать фиктивные bronze/silver/gold события и не считать четыре трофея. Если была bronze, затем сразу platinum — один upgrade bronze→platinum. Повтор того же/меньшего результата — no-op для истории получения.

Evidence snapshot хранит исходные числовые условия, даты, идентификаторы, состав/coverage и версию правила; raw клиентские ответы и внутренние комментарии должны оставаться в защищённом источнике Sandbox, не копироваться в публичный Trophy API. Snapshot с ID и небольшими значениями достаточен для объяснения, но нельзя вместо утраченной истории придумать отсутствующие исходные факты.

Ухудшение качества в новой неделе, поздний возврат, новое задание в каталоге или изменение программы не понижают ранее полученный уровень. Исправление неправильного старого измерения помечает доказательство спорным и требует аудируемого review/revoke, а не незаметного снижения.

### Отзыв

Рекомендуется отзыв конкретного ошибочного события/доказательства, с обязательной причиной. В той же транзакции явно определить новый активный максимум среди оставшихся реальных выдач: platinum→gold допустимо только вследствие **этого явного отзыва**, если gold действительно был получен раньше. Если первая выдача была сразу platinum и других настоящих выдач нет — active tier становится NULL, не выдуманная бронза.

Чтобы resync не выдал отозванную награду вновь по неизменившемуся доказательству, сохранять suppression на source evidence/rule version и/или явный запрет auto-regrant до рассмотрения. Новое доказательство и разрешение повторной выдачи требуют утверждённой политики. Событие source revoked, например TrainingConfirmationEvent.revoked, не заменяет отдельный AchievementEvent.revoke: оно запускает проверку/флаг спорности; автоматическое понижение запрещено выбранной механикой. [S1]

Ручная выдача проходит тем же transaction service, с server-side staff/правом управления, допустимым tier и обязательной причиной. Источник manual не маскировать под автоматический результат курса. Для будущего конструктора достаточно catalog metadata + versioned parameters, валидируемых по схемам известных evaluator_key; произвольный Python/SQL/клиентский expression не нужен.

## 9. События, идемпотентность и конкурентные обновления

### Точки пересчёта по существующему коду

| Источник | Реальная точка записи | Предлагаемый сигнал для evaluator |
|---|---|---|
| Техническая проверка / completion | `sandbox/services/checks.py::run_attempt_check()`, success atomic; `sandbox/services/completions.py::record_completion_after_success()` | technical_success и program_completed, только зачётные факты |
| Ответ наставника | `sandbox/views.py::save_mentor_feedback()` | submission_reviewed с конкретной будущей immutable версией; не считать каждый повтор POST новым review |
| Подтверждение обучения | `roadmap/services/confirmations.py::change_training_confirmation()` | training_confirmed/training_revoked по реальному event.pk |
| Неделя | `traineediary/views/weekly_metrics.py::save_weekly_metric()` | weekly_metric_finalized/corrected по будущему revision ID |
| Переход | `traineediary/models.py::TraineeJourney.move_to_stage()` | stage_entered/quality_fixed по новому StageHistory, учитывая rollback/no-op |
| Успешный ИС | `traineediary/models.py::TraineeJourney.complete_probation()`, staff view completion | probation_completed после сохранения результата, а не при одном move_to_stage(done) |
| Будущие тесты | `assessment/services/results.py::complete_exam_attempt()` | assessment_completed после проверки завершённой неаннулированной попытки |

Наиболее подходящий pattern — предметная запись и durable outbox **в одной atomic транзакции**, а on_commit только будит worker. Один on_commit с Celery.delay без durable записи имеет окно потери между commit и доставкой; безопасный resync частично помогает, но не восстановит перезаписанные решения и метрики. Сейчас только Sandbox technical success и Roadmap confirmations уже имеют соответствующие atomic границы; review и metric writer потребуется обернуть вместе с будущими source событиями. Это предложение, код не менялся. [S1, S5, S7, S9, S11, S13]

Не опираться исключительно на общий post_save: он не охватит QuerySet.update, административные/maintenance пути и семантику «это correction, а не новая неделя». Сервисные точки должны нормализовать события, а reconciliation сверять актуальные trusted факты. [S5 — F/update; S15 — watchdog update; S8–S10 — mutable metrics]

### Предлагаемый алгоритм

1. Принять trusted source событие с `(provider, provider_event_id)`. Проверить schema, владельца, контекст и полноту источника. Сохранить inbox/outbox unique; повтор той же доставки не новая выдача.
2. Построить immutable eligibility evidence из источника, проверить invalidation/correction/coverage. Отдельно различать eligible / not_met / not_applicable / unknown.
3. Вычислить **максимальный** подходящий tier; условия проверять независимо. Не выдавать недоказанные промежуточные уровни.
4. В atomic гарантировать одну UserAchievement через unique(user, definition). Для первой конкурентной вставки использовать get_or_create + DB-constraint/retry, затем select_for_update на entitlement либо заранее существующей user строке. Отсутствующую строку нельзя надёжно «заблокировать» одним select_for_update.
5. Под блокировкой вновь прочитать entitlement/revoke suppression и сравнить candidate rank. Только повышение/новая выдача создаёт event и обновляет projection. Unique idempotency key защищает повторное действие; process status фиксировать с той же транзакцией выдачи.
6. После commit уведомление читает новый event; notification повтор не выдаёт новую награду.

Разные valid proofs одного уровня не должны давать несколько grant событий: сравнение текущего rank под блокировкой предотвращает это даже при разных provider event IDs. Новая исправленная WeeklyMetric должна иметь **новую ревизию/ID события**: дедупликация только по metric.pk навсегда потеряет легитимное повышение после исправления значения. Source digest допустим для безопасного legacy resync, но не заменяет полноценную историю ревизий. [S8, S9]

При задержанных сообщениях correction важна: если ошибочные 96% были исправлены на 80% **до выдачи**, старое superseded событие не должно выдать золото. Если 96% были настоящим результатом одной недели, а 80% — новая другая неделя, прежняя награда сохраняется. Если ошибочная награда уже выдана, только явный revoke. Future revision ledger должен отличать эти сценарии.

### Повторная синхронизация

Предлагается отдельная maintenance команда: dry-run по умолчанию, выбранные пользователи/источники, версии правил, отчёт candidate/unknown/suppressed, fingerprint/expected revision guard, explicit apply. Она использует тот же evaluator и выдающий сервис. Не меняет Sandbox snapshots, StageHistory и старые WeeklyMetric, не создаёт фиктивные исходные события.

В retrospective выдаче evidence.occurred_at может быть настоящей старой датой результата; **recorded_at/granted_at — фактическая дата выдачи сейчас**. Не показывать выдуманную старую дату получения медали. legacy Restore также различает completed_at и recorded_at [S2].

GET Trophy Room/API не выдаёт, не повышает, не создаёт отсутствующую UserAchievement, не вызывает get_current_attempt и не восстанавливает completion. Если projection ещё не обработана, API честно показывает состояние синхронизации; мутации не прячутся в чтение. Есть положительный пример SELECT-only в sandbox progress и roadmap [S3, S12].

## 10. Предлагаемый API и совместимость Trophy Room

Эндпоинты ниже **ещё не существуют**:

- GET `/api/achievements/me/` — коллекция и server stats только текущего пользователя.
- GET `/api/achievements/me/<public_id>/` — безопасные details и paginated история реальных grant/upgrade/revoke.
- При необходимости GET `/api/achievements/users/<user_id>/` — только проверенный staff; не публичный выбор чужого пользователя.
- Позднее защищённые POST grant/revoke для разрешённых staff, с CSRF, reason, operation_id и expected revision; не GET. Отдельный service/permission для определения, кому разрешён отзыв.

Session authentication, права на сервере, корректные 400/401/403/404/409 и private/no-store как в текущем Roadmap API. Источники только server providers, browser не задаёт score/provider/evidence. [roadmap/views.py — api_access/training_action; S1]

Ответ одной линейки: opaque public_id, доступный code для раскрытых наград, title/description, category, secret/revealed, applicable, supported tiers, highest **active** earned tier, display rarity, status, rule version, earned_at/last_upgraded_at, проверяемый next-tier progress либо null и data_quality. Details содержат историю настоящих событий, а не синтетические «все четыре металла». Числовой percent возвращать только для доказуемого счётчика; временные планы и бинарные пороги не превращать в фиктивные 40%.

### Секреты и статистика

До получения secret achievement API не возвращает title, description, condition, thresholds, доказательства, progress, специализированный art и семантический code вроде `clean_week`. Публичный UUID может быть opaque. Общая заглушка, secret=true и согласованная публичная редкость/категория — достаточны для фильтра. Нельзя спрятать название только CSS, сохранив его в JSON.

Статистика: один count на **активно полученное определение**, rarity — максимальный текущий уровень, история не увеличивает счётчик. denominator — согласованный применимый активный каталог, включая скрытые placeholders только по утверждённой политике; not_required не равно earned. Отозванные активные выдачи не считаются полученными, но остаются в private history. Нужны server counts для фильтров/пагинации и статистики, чтобы клиент не считал весь каталог по одному page.

## 11. Необходимые миграции — план, не созданные файлы

1. Initial `achievements`: Definition, Tier, UserAchievement, AchievementEvent, SourceEvent/outbox, уникальность user/definition и provider/event_id, индексы history/outbox, валидные действия/ранги, защита журналов и FK. Каталог пяти линеек + утверждённых extras — отдельный versioned seed без пользовательских наград.
2. Источник Sandbox: журналы environment/check execution/submission/review, version/coverage metadata и frozen requirements. Нельзя добавлять их с fake first submission или default «история полная» существующим attempts.
3. Метрики: ревизии/period/finality/coverage и provenance фиксации качества. Старые nullable даты/полноту оставить unknown. Не исправлять автоматически Week start на понедельник.
4. Учебный результат: normalised evidence в owning provider/import приложении либо минимальном слое интеграции, без второй системы адаптации. Поля score/start должны оставаться nullable для manual-only исторических подтверждений.
5. После отдельных dry-run и утверждения — source-based backfill только реально доказанных наград. Никакой выдачи в обычной миграции схемы/GET и никакого «восстановления» промежуточных уровней ради красивой истории.

Приоритет: для первого безопасного выпуска достаточно пунктов 1 и hooks на готовые положительные доказательства. Остальные источники добавляются прежде запуска зависимых повышенных/секретных правил. Новые миграции не создавались и не применялись.

## 12. Предлагаемый порядок реализации

1. Согласовать календарные границы/первый неполный день, смысл restart/first try, независимость условий платины от лимита resets, weekly vs final quality, полную неделю и редкости extras.
2. Ввести общий каталог/tiers/entitlements/append-only events/outbox и единый атомарный grant/upgrade/revoke service; тесты direct platinum, races, repeated delivery, suppression после отзыва и rollback.
3. Реализовать только готовые providers: manual training bronze, technical Sandbox bronze, технические milestones и NEW_HIRE probation. Для спорной истории — unknown, без backfill по current stage.
4. Реализовать строгий stage/period resolver для ограниченных weekly quality/speed и подтверждённого входа NO_REVIEW. Не менять readiness thresholds и смысл текущих метрик.
5. Сделать GET API read-only, серверное скрытие секретов, правильную статистику и условную applicability. Затем отдельной задачей интегрировать Trophy Room с реальными DTO и палитрой повышаемого медальона.
6. Ввести полные Sandbox источники и проверку coverage; только после этого включить gold/platinum/«Без замечаний» для доказанных новых процессов.
7. Ввести finalised full-week/metric-revision evidence, затем streak и «Чистую неделю». Подключить Teachbase/course adapter для timed/scored training tiers.
8. Безопасный resync: dry-run на выбранных синтетических/затем согласованных обезличенных данных; production apply — отдельное согласованное действие.

Будущие проверки должны покрыть границы условий, неоднозначный legacy, catalog drift, удалённые детали при сохранённом snapshot, упражнения attempt_number>1, повтор того же review, возвращённый credit answer при активной тренировке, correction до/после выдачи, обратный порядок очереди, пропуски/возвраты, terminated ИС, internal_transfer, secret JSON redaction, GET SELECT-only и настоящие PostgreSQL конкурентные обновления. Это рекомендации; такие новые тесты в аудите не писались и не запускались.

## 13. Риски и решения, требующие согласования

- **Ложная платина по нулям.** attempts_count=1, restart_count=0 и последнее approved не доказывают полную чистую историю. Единственный current state — положительный факт сейчас, не доказательство отсутствия старых замечаний. [S4–S7]
- **Состав и обязательность меняются.** Технический snapshot защищает бронзу, но для текста/рестартов нужны frozen требования и отдельные исторические факты. JSON ID переживает удаление, FK детали — нет. [S2, S4]
- **Возвраты качества.** Текущая фиксация очищается, latest week не фильтруется по посещению; reuse readiness/_get_latest_metric для наград даст ложное соответствие этапу. [S9, S10]
- **Legacy full week неизвестна.** Недатированная запись/одиночная 100%/три номера подряд не доказывают полный календарный период и фактическую выборку. [S8, S9]
- **Модели записи не все append-only.** WeeklyMetric/TaskAttempt/CheckRun обычные mutable модели. StageHistory и WeeklyMetric закрыты для редактирования в Django admin, но это не DB-trigger или глобальный ORM запрет. Сервис completion допускает nullable completed_by; старые записи без автора требуют разбирательства, а не автоматического успеха. [S4, S8, S11, traineediary/admin.py — StageHistoryAdmin/WeeklyMetricAdmin]
- **Особенность Roadmap audit guard.** `TrainingConfirmationEvent.save()` запрещает повторное сохранение загруженного instance через `_state.adding`, но не устанавливает force_insert для нового instance с явным существующим PK. Django Model._save_table() может в этом случае выполнить UPDATE; это возможный внутренний ORM-обход append-only, не открытый HTTP endpoint. В SandboxProgramCompletion.save() force_insert уже есть. Для будущего AchievementEvent нужен как минимум аналогичный insert-only guard, а при требованиях к абсолютной неизменяемости — DB-уровень. Этот вывод сделан по коду, без изменения/эксплуатации данных. [roadmap/models.py — TrainingConfirmationEvent.save(), строки 46–49; .venv/lib/python3.13/site-packages/django/db/models/base.py — Model._save_table(); sandbox/models.py — SandboxProgramCompletion.save(), строки 125–133]
- **Уровни не всегда логически вложены.** Буквальная sandbox platinum не включает reset limit; качество имеет только три основных уровня. Не строить общую бизнес-логику, требующую получения всех промежуточных уровней. [условия задачи; S4–S7]
- **Отзыв и resync.** Без suppression система вернёт ошибочно отозванную награду по тому же старому source. Обычное ухудшение результата и correction ошибочного proof надо различать; автоматическое понижение запрещено механикой.
- **Роли в прошлом.** Проверка current is_staff не является неизменным доказательством роли автора много лет назад. Новые source events должны фиксировать доверенный provider/авторизацию в момент записи. Удалённые SET_NULL авторы старой истории — unknown, не автоматически обвинение в недостоверности. [S1, S8, S11, S12]
- **Результат Assessment не равен Teachbase.** Его баллы уже реальны для конкретного экзамена, но связи с завершением учебной программы не показано. Нельзя использовать exam score как score всей программы без явного mapping и правила. [S13]
- **Нет реального аудита production-истории.** Прочитанные tests фиксируют известные сценарии и оговорки, но не подтверждают coverage всех реальных сотрудников. Existing Django suite в этом аудите не запускался; результаты предыдущих задач не выдаются за новый прогон.

На согласование нужны: политика первой неполной даты и календарного day 1; counting resets/infrastructure errors; first five submissions vs catalog order; weekly/final quality; определение full week/полной выборки; применимость extras внутренним сотрудникам; редкости extras; explicit revoke/regrant и секретная статистика. До согласования и полноценного источника не запускать зависимые высокие/секретные награды.
