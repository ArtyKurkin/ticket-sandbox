# Sandbox Completion Snapshot

## Модель и правило уникальности

`sandbox.SandboxProgramCompletion` хранит первый технический результат на пару `(user, program_key)`. На эту пару задано ограничение UNIQUE в БД. Для текущего MVP стабильный идентификатор программы — `l1`. Fingerprint описывает состав первого завершения; новый состав этой же программы не создаёт второе завершение и не заменяет первое.

| Поле | Назначение |
|---|---|
| user | Ссылка на пользователя с PROTECT, чтобы удаление аккаунта не уничтожало результат |
| program_key | Стабильный ключ программы l1; не FK на удаляемую очередь |
| completed_at | Максимальное время доказанного технического успеха среди обязательных заданий |
| recorded_at | Время записи факта; для legacy может существенно отличаться от completed_at |
| source | technical_check либо legacy_restore |
| composition_fingerprint | SHA-256 от версии формата, ключа программы и отсортированных ID обязательных заданий |
| snapshot | JSON версии 1 с составом и минимальными идентификаторами доказательств |

Пример элемента `snapshot.tasks`:

```json
{
  "task_id": 101,
  "task_slug": "nginx-example",
  "order": 1,
  "attempt_id": 201,
  "evidence_source": "technical_passed_at",
  "passed_at": "2026-10-13T10:00:00+00:00",
  "check_run_id": 301
}
```

Пример иллюстрирует формат; демонстрационные результаты в БД не добавляются. Снимок не содержит ответов клиента, комментариев, логов проверки, настроек окружения или полной копии TaskAttempt/CheckRun. Идентификаторы доказательств намеренно не являются FK: удаление Task, попытки или проверки не удаляет исторический результат. Slug и порядок задания сохраняются как небольшая справочная подпись исходного набора.

Снимки запрещено редактировать и удалять через model.save/delete, QuerySet.update/delete/bulk_update/bulk_create. Даже новый объект с существующим PK выполняет INSERT, а не UPDATE. Админка предоставляет только просмотр. Формат, непустой уникальный набор и соответствие fingerprint проверяются при создании. Неизменяемость обеспечивается приложением и админкой; прямой SQL, save_base и schema rollback являются привилегированными обходами, а не поддерживаемыми операциями сервиса.

## Момент фиксации и параллельность

После `check.sh` с exit_code=0 существующий `run_attempt_check`:

1. Подготавливает обычный результат проверки и обработку окружения.
2. В одной `transaction.atomic` сохраняет успешный CheckRun и технические поля TaskAttempt.
3. Вызывает `record_completion_after_success(attempt_id=..., check_run_id=...)`.
4. Создаёт снимок только если триггер — зачётная попытка обязательного активного задания активной очереди l1 и все текущие обязательные задания имеют доказательства.

Docker-вызовы выполняются до этой короткой DB-транзакции. При ошибке фиксации транзакция откатывает новый CheckRun, дату зачёта и снимок вместе; технический результат не оказывается отдельно подтверждённым в БД без требуемого снимка. Обычный обработчик worker-ошибок остаётся прежним. Уведомление о завершении отправляется существующим callback после commit.

Дополнительная тренировочная попытка, неуспешный CheckRun, пустой набор, неактивная очередь и успех необязательного задания не создают завершение. Повторная техническая проверка уже зачтённой попытки остаётся заблокирована. Повторный явный вызов фиксации возвращает существующую запись без изменения времени и JSON.

Write-сервис блокирует строку очереди и все её задания, включая неактивные, перед определением состава. В PostgreSQL блокировка очереди также конфликтует с FK-вставками новых заданий; блокировка Task защищает от изменения активности, порядка и удаления выбранных строк. После получения блокировок существующее завершение проверяется повторно. `get_or_create` и UNIQUE защищают от конкурирующего INSERT.

SQLite не поддерживает эти row locks. Для самостоятельных вызовов write-сервиса предусмотрены ограниченные повторы всей транзакции при SQLITE_BUSY/SQLITE_LOCKED. Внутри внешней транзакции savepoint автоматически не повторяется: ошибку должен обрабатывать её владелец. Проверка двух параллельных вызовов выполнена на SQLite и на отдельном временном PostgreSQL 16. Конкурентные изменения реального каталога и параллельные последние worker-проверки на обезличенной рабочей копии остаются отдельным проверяемым сценарием перед выпуском.

Снимки не создаются в миграции, GET, dashboard, сервисе чтения прогресса или просмотре React. Завершение программы не переводит этап TraineeDiary.

## Правила доказательств и legacy

Применяются неизменённые правила Foundation: technical_passed_at либо CheckRun этой же попытки №1 с result=passed и exit_code=0. `status=passed`, `check_status=passed` и решение наставника approved сами по себе не доказывают успех. Тренировки исключены. В снимок включается источник, время доказательства и ID успешного CheckRun, когда он доступен. Будущие некорректные даты не дают кандидату право на фиксацию.

Schema migration `0031_sandbox_program_completion` только создаёт таблицу. Исторические попытки, проверки, статусы и даты не переписываются; даже доказанное прежнее завершение автоматически не получает запись.

Отдельная команда по умолчанию выполняет **только чтение**:

```sh
python manage.py restore_sandbox_completions --json
python manage.py restore_sandbox_completions --user-id 123 --json
```

Без user-id анализируются пользователи с зачётными попытками в l1. Отчёт показывает eligible/reason, fingerprint, текущий проверенный состав, доказательства, предложенное completed_at и существующий completion_id. Он не создаёт записи и не заполняет technical_passed_at. Текстовый отчёт помечен DRY RUN.

После проверки владельцем данных допускается явная запись для перечисленных пользователей:

```sh
python manage.py restore_sandbox_completions \
  --apply --user-id 123 \
  --expected-fingerprint '<fingerprint из проверенного отчёта>'
```

`--user-id` можно повторять. `--apply` без явных пользователей и ожидаемого fingerprint запрещён. Состав и доказательства повторно проверяются под блокировками. Если состав изменился или хотя бы один новый результат не доказан, выбранная операция откатывается целиком. Повторное применение возвращает существующее завершение. Режим без --apply не меняет данные даже при переданном fingerprint.

**Граница восстановления:** моделей версий программы раньше не было. Команда подтверждает только доказанный текущий состав, явно выбранный оператором; восстановить неизвестный набор, обязательный в прошлом, она не может. Деактивированные/удалённые задания и неполные исторические данные требуют отдельного согласованного разбора. source=legacy_restore и recorded_at отличают такую запись от автоматической фиксации при новой проверке. Для неоднозначных попыток остаётся read-only команда `audit_sandbox_progress`.

Эти maintenance-команды запускает доверенный серверный оператор; HTTP-пути записи не добавлены. В задаче восстановление выполнялось только в изолированных тестах, не на реальных пользователях.

## Контракт чтения

Прежние функции `build_sandbox_queue_progress` / `build_sandbox_queue_progress_map` и все существующие поля DTO сохранены. Добавлены:

| Поле/свойство | Значение |
|---|---|
| is_completed | Есть сохранённый SandboxProgramCompletion для пользователя и программы |
| completion_id | ID сохранённого факта либо None |
| completed_at | Историческое время технического завершения либо None |
| completion_fingerprint | Fingerprint сохранённого состава |
| completion_task_ids | Неизменённые ID заданий сохранённого состава |

`is_technically_completed`, `is_ready`, passed_count, remaining_count, total_count и progress_percent по-прежнему описывают **текущий активный набор**. `is_completed` описывает сохранённый факт. Если текущий набор полностью выполнен, но снимка ещё нет, `is_technically_completed=True`, `is_completed=False`: чтение не выдаёт историческое завершение автоматически.

После добавления нового задания возможны `is_completed=True`, `is_technically_completed=False` и текущий прогресс 15/16. После удаления/деактивации всех заданий текущая программа не считается успешно пройденной как 0/0, но сохранённое завершение остаётся истинным. Это работает также после деактивации или удаления очереди; чтение программы производится по стабильному ключу l1.

Текстовые показатели по текущим обязательным заданиям остаются независимыми:

- needs_revision — прежний needs_revision_count;
- waiting_for_review — on_review_count;
- answer_not_submitted — unsubmitted_count;
- unread_mentor_feedback — unread_feedback_count.

Они меняются при работе с ответами и не обновляют снимок. Snapshot не используется как замена текущих показателей текста или качества. Batch теперь выполняет четыре SELECT для непустой очереди: сохранённые завершения, очередь, задания, зачётные попытки. Никаких записей при чтении нет.

TraineeDiary продолжает использовать прежние показатели текущего набора для readiness. Схемы legacy/unified, рабочие критерии качества/скорости, ручные переходы, StageHistory и завершение ИС не менялись. Будущий Roadmap должен явно сериализовать is_completed и исторические поля отдельно от текущего прогресса; API сейчас не создаётся.

## Локальная проверка и ограничения

Только изолированная БД, без production-подключения:

```sh
export DEBUG=True DB_ENGINE=django.db.backends.sqlite3 SENTRY_DSN=''
export DB_NAME="$(mktemp -t sandbox-completion-audit)"
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py migrate --check
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test --noinput
.venv/bin/python manage.py restore_sandbox_completions --json
```

Тесты проверяют новую автоматическую фиксацию, повторный check, два параллельных вызова, SQL-уникальность, изменения/удаление каталога, независимость ответов/тренировок, чистоту чтения, atomic rollback, безопасное восстановление, права и сохранение обеих схем TraineeDiary. Миграционный тест на отдельном SQLite-соединении сравнивает исходные попытки и CheckRun до/после и проверяет отсутствие backfill.

Проверка на новом изолированном PostgreSQL 16 с синтетическими данными выполнена: миграции, system checks и 66 связанных тестов, включая параллельную фиксацию. Сервер использовал только Unix-сокет в /tmp, TCP был отключён; кластер остановлен и удалён. Обезличенная рабочая копия не предоставлена: перед отдельным выпуском требуется проверка её каталога и реальных профилей данных. Реальные базы в этой задаче не читались и не менялись.

Снимок фиксирует состав по ID, не версии файлов check.sh или содержимого задания. Модель сохраняет один результат на пользователя/program_key, не на адаптацию или каждую версию каталога. Повторное обучение как новая программа требует нового стабильного ключа и отдельного решения. Привязка к текущему slug очереди предполагает, что ключ l1 сохраняет своё назначение; повторное использование l1 для другой программы запрещено концепцией идентичности.

Результат защищает удаление аккаунта пользователя через PROTECT. Удаление персональных данных или исправление ошибочного завершения требует отдельного согласованного процесса. Откат миграции после появления записей удалит таблицу результатов; такой откат нельзя выполнять как обычную безопасную операцию. Snapshot не содержит DB-trigger защиты от привилегированного SQL.

React Roadmap, Trophy Room, API, production-конфигурация и CI/CD не изменены. Commit, push и деплой не выполнялись.
