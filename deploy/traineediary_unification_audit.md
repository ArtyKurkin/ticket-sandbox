# TraineeDiary: аудит перед переходом на единую программу

Статус на 03.11.2026: подготовлен автономный read-only аудит рабочей схемы
`d4aa79c0e4fa5e49cc98e0a27e40319fb7e49a29`. Оператор передал результаты
read-only аудита: 14 legacy-адаптаций, из них 11 в «Выход с ИС» (5 success,
6 terminated), 3 активных; 64 StageHistory, 37 WeeklyMetric и 0 подтверждений
Roadmap. Профиль `confirmed_2026_10_30`, блокирующих legacy-карточек нет.
Согласованная [сводка baseline](traineediary_unification_baseline_2026-11-03.json)
содержит предоставленные контрольные суммы, без персональных данных.

Подготовка переноса и тестов описана в [плане внедрения](traineediary_unification_rollout.md).
Production-перенос не разрешён: `migration_authorized=false`. Deploy и push
не выполнялись. Ниже сохранена методика первоначального read-only аудита.

## Что читает аудит

[Скрипт](audit_traineediary_unification.py) запускается отдельно от Django и
использует установленный в Web `psycopg` и существующие переменные `DB_*`.
Он не читает `.env`, не инициализирует Django, Celery, Sentry или Docker client.

| Источник | Читаемые данные и назначение |
| --- | --- |
| `traineediary_traineestage` | Каталог, применимость к схемам и типам входа, порядок, сроки и веса; проверка соответствия контракту 0007 |
| `traineediary_traineejourney` | Текущий этап, схема, тип входа, исходные даты, качество, результат ИС, FK и комментарии; количества, целостность и общий отпечаток |
| `traineediary_stagehistory` | Все исходные переходы, даты, авторские FK и заметки; непрерывность, единственная открытая запись, соответствие текущему этапу и отпечаток |
| `traineediary_weeklymetric` | Недельные показатели, даты, комментарии наставников и цели; допустимость значений, уникальность недель, связи и отпечаток |
| `roadmap_trainingconfirmationevent` | Подтверждения/отмены обучения, FK, даты и комментарии; связи, последнее подтверждение и отпечаток |
| `auth_user` | Только `id` и `is_staff` для проверки FK и правил доказательства переходов Roadmap; имена, email, логины и пароли не запрашиваются |
| `django_migrations` | Только `app` и `name` для TraineeDiary/Roadmap; наличие записей о 0007 и начальной миграции Roadmap |

Тексты комментариев и заметок читаются в память только для общего SHA-256
исходных строк и подсчёта непустых полей. Содержимое, индивидуальные хеши,
идентификаторы сотрудников/адаптаций/авторов, персональные даты и значения
метрик по отдельным людям не выводятся. Неизвестные значения категорий
заменяются на `__unknown__`, чтобы произвольный текст не попал в JSON.

Аудит не читает таблицы Ticket Sandbox и наград и не запускает их расчёт.
Он проверяет ссылки и доказательства TraineeDiary/Roadmap, но не проверяет
зачёты отдельных заданий Sandbox или состояние Terminal Broker Lite.

## Гарантии выполнения

- Открывается одно отдельное соединение PostgreSQL с
  `default_transaction_read_only=on` только для этой сессии.
- Все запросы данных выполняются внутри явной транзакции
  `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`.
  Скрипт проверяет действующие параметры транзакции перед чтением.
- Согласованный снимок завершается явным `ROLLBACK`, включая путь ошибки.
  SQL ограничен `SELECT` и управлением собственной read-only транзакцией;
  ORM, миграций, DDL, записей и блокировок `FOR UPDATE` нет.
- Таймаут подключения — 5 секунд, каждого запроса — 15 секунд,
  ожидания блокировки — 2 секунды, бездействия в транзакции — 60 секунд.
  Обычные блокировки PostgreSQL при чтении не исключаются.
- Ошибки выводятся как короткий JSON с SQLSTATE, без сырых сообщений PostgreSQL,
  SQL, реквизитов подключения или содержимого строк.
- Скрипт не перезапускает контейнеры, не меняет их конфигурацию и не обращается
  к Docker API, Scheduler, Worker или Terminal Broker.

## Команда для ручного запуска

Скопировать **только этот скрипт** на хост сервера, например в
`/tmp/audit_traineediary_unification.py`. Обновлять checkout приложения,
добавлять management command или применять миграции не требуется.

На хосте выполнить:

```sh
docker exec -i training-platform-web python -B - < /tmp/audit_traineediary_unification.py
```

`docker exec` создаёт отдельный короткоживущий процесс аудита в существующем
Web-контейнере. Python читает скрипт со stdin; `-B` запрещает запись bytecode.
Рабочие процессы Web и Broker не перезапускаются. Пароли не передаются
в командной строке и не выводятся: используются уже имеющиеся `DB_*`.

При необходимости сохранить результат на хосте в файл с закрытыми правами:

```sh
(umask 077; docker exec -i training-platform-web python -B - < /tmp/audit_traineediary_unification.py > /tmp/traineediary_unification_audit.json)
```

Код 0 означает, что аудит выполнен, включая случаи найденных неоднозначностей.
Код 1 и `status=error` означают ошибку выполнения. `ready_for_mapping_review`
означает только отсутствие найденных блокирующих проблем; разрешение на перенос
всегда остаётся `migration_authorized=false`.

Версия приложения указана в JSON как **ожидаемая**, а не независимо проверенная:
скрипт не выполняет Git-команды на сервере.

## Что смотреть в JSON

- `counts`, `by_scheme_entry_and_stage`, `by_scheme_and_completion_status`:
  размеры обеих схем, текущие этапы и записанные результаты ИС.
- `probation_evidence`: отдельно подтверждённые success/terminated и
  `insufficient_data`; положение в «Выход с ИС» само по себе успех не доказывает.
- `proposed_mapping`: сколько карточек каждого типа входа затронет каждое
  соответствие этапов. Это предложение для просмотра, а не исполненный перенос.
- `integrity`: агрегированные количества по кодам проблем, предупреждениям
  и числу затронутых legacy-карточек. Номера сотрудников не раскрываются.
- `theory`: частично посещённые теоретические этапы. Посещение всех пяти
  этапов не трактуется как подтверждение завершения обучения.
- `naive_progress_recalculation`: сколько процентов прогресса изменилось бы
  при простой смене каталога; выводятся только количества lower/equal/higher.
  Такой пересчёт не предлагается применять.
- `roadmap`: последнее подтверждение обучения и уже доказанные завершения
  рабочих этапов по действующим правилам. События и зачёты не создаются.
- `preservation_baseline`: количества строк и общие SHA-256 всех исходных
  полей каталога, карточек, истории, метрик и подтверждений Roadmap.

Отпечатки фиксируют только состояние согласованного снимка. Они не являются
backup и не доказывают сохранность после ещё не выполненного переноса.
При продолжающейся работе изменения допустимы: перед будущим переносом нужен
свежий аудит в согласованном окне, а сравнение — в том же окне без записей.

## Предлагаемая таблица соответствий

| Старый этап | Этап единой программы | Правило |
| --- | --- | --- |
| Первый день (`first-day`) | Программа обучения (`training-program`) | Сохранить исходную историю и частичный прогресс |
| VDS (`vds`) | Программа обучения | То же |
| Управляемые сервисы (`managed-services`) | Программа обучения | То же |
| Клиентский сервис (`client-service`) | Программа обучения | То же |
| Перед выходом в тикеты (`before-tickets`) | Программа обучения | Отдельно проверить случаи после Sandbox |
| Задания в ticket-sandbox (`sandbox-candidate`) | Задания в Ticket Sandbox | Тот же ID этапа и существующие доказательства |
| В тикетах с проверками (`with-review`) | В тикетах с проверками | Тот же ID этапа |
| Кнопка по желанию (`optional-review`) | Проверки по желанию | Тот же ID; меняется только отображаемое название |
| Без проверок (`no-review`) | Без проверок | Тот же ID этапа |
| Выход с ИС (`done`) | Выход с ИС | Та же адаптация, результат, даты и 100% прогресса; без создания новой |

Внутренним переходам сохраняются только рабочие этапы и «Выход с ИС»;
теория и Sandbox не становятся обязательными. Если в исходных данных уже
есть неприменимая теория, случай требует отдельного разбора.

## Неоднозначности и дальнейший план

1. Проверить актуальное число в «Выход с ИС» и полноту результата ИС.
   Отсутствующие подтверждения, даты и причины не восстанавливать догадками.
2. Разобрать неизвестный/смешанный каталог, пробелы и пересечения истории,
   несколько открытых записей, отсутствующие связи и неприменимые этапы.
3. Учесть различие двух допустимых старых каталогов: в исходном варианте
   `before-tickets` расположен после Sandbox, а в подтверждённом историческом —
   перед ним. Объединение теории не должно аннулировать уже доказанный Sandbox
   или автоматически подтверждать оставшуюся теорию.
4. После просмотра JSON согласовать окончательное соответствие и реализацию.
   Предлагается изменить только схему и текущий этап существующих карточек,
   записав отдельное происхождение переноса. Исходные StageHistory, даты,
   комментарии, WeeklyMetric, качество и результат ИС не переписывать.
5. Историю интерпретировать в новой схеме через явную запись переноса, сохраняя
   исходные названия в истории. Для незавершённого этапа сохранить прежнюю
   формулу прогресса до следующего настоящего перехода. Подтверждения обучения
   и награды из положения на доске или прошедшего времени не создавать.
6. Подготовить идемпотентную миграцию с проверкой свежего аудита и тестами
   сохранности полей, повторного запуска, завершённых ИС, внутренних переходов,
   частичной теории и неизменности доказательств Roadmap.
7. После отдельного разрешения и успешного переноса скрыть пустую legacy-доску
   штатной логикой канбана. Для отката представления предусмотреть отдельный
   снимок прежнего распределения только для чтения; исходные данные не удалять.

До отдельного разрешения перенос не запускается. Для будущего окна необходимы
успешный dry-run с актуальной БД и совпадение с рассмотренным baseline.
После переноса использовать `unify_stage_schemes --verify`: исходный автономный
аудит v1 не интерпретирует записи происхождения новой схемы.

## Локальные проверки скрипта

03.11.2026 успешно пройдены 24 теста аудита: 21 проверка на синтетических
данных и 3 на одноразовом локальном PostgreSQL 16. Это проверки скрипта аудита;
миграция этим прогоном не проверялась. Результаты последующего операторского
аудита и подготовка переноса приведены в начале документа и плане внедрения.

```sh
.venv/bin/python -B -m unittest deploy.tests.test_traineediary_unification_audit -v
```

Для дополнительных проверок на одноразовом локальном PostgreSQL 16 без TCP:

```sh
TP_AUDIT_POSTGRES_BIN=/path/to/postgresql16/bin .venv/bin/python -B -m unittest deploy.tests.test_traineediary_unification_audit -v
```

Тестовый кластер создаётся только во временном каталоге и удаляется после
завершения. При этом проверяются реальная read-only транзакция, отказ записи
даже владельцу БД и неизменность всех исходных строк. Таблицы и записи в этих
тестах синтетические; рабочие базы и Docker не используются.
