# Репетиция обновления PostgreSQL

Сценарий `deploy/rehearse_database_upgrade.py` проверяет обновление исходной
ревизии `92a1123486c1e8ca348ce28e8726944532bed63b` до явно выбранного коммита.
Это отдельная операция на изолированной копии, без deploy и переключения Lite.
Без `--execute` выводится только план: Docker, БД и файловая система не меняются.

## Зафиксированный результат

Репетиция администратора от **30.10.2026** завершилась успешно на изолированной
копии реальной БД. В Git сохранена только согласованная сводка:
[результат репетиции](database_rehearsal_2026-10-30.md). Архив БД, исходный
report.json, сведения о пользователях и приватные реквизиты в репозиторий не входят.

Внедрение не выполнялось. Следующее рассмотрение внедрения — **02.11.2026**,
после отдельного решения и проверки актуального состояния платформы.

## Условия подготовки

- Сценарий выполняется на локальном Linux Docker-хосте. Source revision и
  назначение основной БД проверяются только в режиме нового backup.
- Application image должен быть заранее собран из точного целевого коммита,
  закреплён immutable ID и содержать OCI label `org.opencontainers.image.revision`
  с полным SHA этого коммита. Сценарий не собирает и не скачивает образы.
- Каталог backup находится вне Git, принадлежит пользователю запуска и имеет
  права 0700; файлы — 0600. Используется согласованное защищённое хранилище.
- Нужны PostgreSQL 16, минимум 3 GiB доступной RAM и запас диска для backup,
  новой копии, WAL и индексов. Проверка ресурсов повторяется перед созданием копии.
- Флаг `TERMINAL_BROKER_ENABLED=false` сохраняется в проверочных контейнерах.

## Существующий backup без нового чтения основной БД

`--reuse-backup-report` указывает на приватный прежний report.json, рядом с которым
находится database.dump. Проверяются source revision, backup.valid, TOC status,
размер, SHA-256, PGDMP header, владение и права файлов. После создания новой копии
повторяется `pg_restore --list` и проверка обязательных таблиц.

В этом режиме нет pg_dump, запросов к основной PostgreSQL, инспектирования
действующих web/db или изменений прежних report.json и database.dump.
`--postgres-image` задаёт локальный immutable ID образа PostgreSQL 16.

Команда просмотра плана; значения переменных подготавливает администратор:

```bash
python3 -B deploy/rehearse_database_upgrade.py \
  --target-revision "$TARGET_REVISION" \
  --target-image "$TARGET_IMAGE_ID" \
  --backup-root "$BACKUP_ROOT" \
  --reuse-backup-report "$PREVIOUS_REPORT" \
  --postgres-image "$POSTGRES_IMAGE_ID"
```

Только после отдельного разрешения к этой команде добавляется `--execute`.
При новом backup параметры reuse не передаются: сценарий дополнительно проверяет
источник, выполняет read-only SELECT и ограниченный по времени pg_dump.
Оба режима требуют спокойного окна и проверки ресурсов хоста.

## Изоляция, restore и проверки

Каждый запуск создаёт новые UUID-container/volume с owner labels. Коллизии
останавливают работу; существующие ресурсы не принимаются и не удаляются.
PostgreSQL-копия использует `network=none`, без опубликованных портов. Контейнеры
приложения разделяют только её network namespace, без Docker socket и mounts.

Bootstrap-администратор копии — rehearsal_admin. Отдельная rehearsal владеет
восстановленной БД и объектами; в режиме reuse она сразу создаётся без SUPERUSER,
CREATEDB и CREATEROLE. Подробности: [исправление restore](restore_rehearsal_fix.md).

Restore выполняется с `--single-transaction --exit-on-error --no-owner
--no-privileges`. Любой ненулевой exit code останавливает работу. Количества строк
не заменяют успешный restore. Все подшаги имеют отдельные безопасные статусы.

До и после миграций проверяется общий frozen-контракт
[исторического каталога](catalog_0007_rehearsal.md), точный pending/applied plan,
legacy-схемы прежних journeys, отсутствие массовой выдачи наград и потерь зачётов.
Для всех исходных public-таблиц сравниваются количества и SHA-256 всех исходных
колонок, включая ID, FK, даты, тексты, статусы, историю и недельные метрики.
Sequence не должны исчезать, менять шаг/cycle или уменьшать счётчик.

Новые служебные поля исключаются из сравнения по сохранённому списку старых
колонок. Допускаются только ожидаемый новый training-program, штатная framework
metadata и точно согласованный набор миграций. Все исходные framework-записи
также сравниваются; назначения прав пользователям и группам сохраняются.

## Диагностика и границы результата

report.json содержит статусы, количества и отпечатки. Сырые stdout/stderr,
SQL, пароли, пользовательские строки и приватные exception messages не выводятся.
Архивы, исходные отчёты и credential-файлы не публикуются в Git или CI artifacts.

PASS в режиме reuse относится только к историческому снимку:
`readiness_scope=historical_snapshot_only`. Новые записи основной БД не проверены.
Перед реальным обновлением необходимы отдельное разрешение, финальный backup
в окне без записей и проверка текущей БД. Восстановление старого backup поверх
действующей БД потеряет новые записи. Обратная миграция 0007 и `--fake` не являются
способом обхода несовместимости. Сценарий не выполняет deploy или откат и ничего
не очищает автоматически; адресная остановка/удаление копии — отдельное решение.
