# CI и ручной CD

## Текущее состояние

`ci.yml` запускает проверки на push и pull request на GitHub-hosted runner.
Job `deploy-staging` удалён: тесты больше не получают SSH-секреты, не подключаются
к серверу и не пересоздают сервисы. Все прежние CI-проверки сохранены.
`manage.py migrate` остался только для временной SQLite-базы `ci-sync-check.sqlite3`
при проверке каталога на runner; это не миграция серверной БД.

`manual-deploy.yml` — **заблокированный шаблон**, а не работающий деплой.
Он принимает запрос только через `workflow_dispatch` из `main`:

- target — только `staging`, production отсутствует;
- revision — полный lowercase SHA из 40 символов, доступный в истории `origin/main`;
- confirmation — точная строка `DEPLOY STAGING <SHA>`;
- валидация исполняет доверенный код workflow-ревизии, не код выбранного релиза;
- будущий deployment-job требует `MANUAL_STAGING_DEPLOY_ENABLED=true` и
  environment `manual-staging`, но пока **всегда завершается ошибкой до доступа
  к серверу**, даже если переменная выставлена и approval пройден.

В шаблоне нет SSH, Docker, миграций, адреса сервера или чтения deployment-секретов.
Успех validation-job означает только проверенный запрос, а не успешный деплой.
Production-вариант этим изменением не реализован.

Изменения начинают защищать push в main только после согласованного применения
этого исправления в main. Уже запущенные/ожидающие старые deploy-job используют
старую ревизию workflow; оператору нужно отдельно проверить их и отменить
до публикации исправления. В рамках подготовки никакие runs не отменялись.

## Почему прежнюю последовательность нельзя перенести

В базовом Compose и prod overlay `TERMINAL_BROKER_ENABLED` явно не закреплён.
Он может приходить из `.env.prod`, а значение по умолчанию в Django — `false`.
Scheduler находится в отдельном профиле `terminal-broker`; прежний workflow
пересобирал/пересоздавал Web и Worker, не согласовывая с ним версию и настройки.
Он также выполнял общий `migrate`, синхронизацию каталога, сборку учебных образов
и принудительное пересоздание Gateway без отдельного плана этих изменений.

Такой сценарий способен заменить контейнеры, созданные с дополнительными
настройками пилота, конфигурацией, разрешённой двумя базовыми Compose-файлами.
Это совместимо с сообщённым оператором состоянием Web=false, Worker=false,
Scheduler=true, но не доказывает причину инцидента 03.11.2026. Сервер при
подготовке исправления не исследовался; `.env.prod` и фактический набор
runtime overrides неизвестны. Изменение CI не исправляет существующий рассинхрон.

Название прежнего job «staging» не доказывает изоляцию: нельзя переносить его
SSH-реквизиты и путь `/opt/training-platform-compose/app` в новый workflow,
считая действующую платформу безопасным staging по названию.

## Безопасное включение реального ручного CD

1. Отдельно согласовать применение CI-исправления в main; до этого push/merge
   не выполняются. Сам merge после исправления запускает только CI, а не деплой.
   Сделать `Check CI and manual CD boundaries` (job `workflow-policy`)
   обязательной проверкой ветки и требовать review
   изменений workflow, guard и deployment-процедуры.
2. Подтвердить отдельный staging: host identity, Compose project, пути и БД
   не должны указывать на действующую платформу. Production не добавлять
   в choices или в fallback. Разбор/восстановление действующего пилота —
   отдельная согласованная операция, не побочный эффект CD.
3. Заранее создать GitHub environment `manual-staging`: required reviewers,
   prevent self-review, разрешённая ветка только main; запретить обход protection
   администратором, если настройка доступна. Проверить эти правила реальным
   запросом approval без серверной операции. YAML сам правила не устанавливает;
   при отсутствии нужной защиты на тарифе workflow оставлять заблокированным.
   Реквизиты будущего staging хранить только в этом environment и не переиспользовать
   repository-level реквизиты действующего сервера.
4. Подготовить отдельным reviewed изменением процедуру с read-only preflight:
   успешный CI именно выбранного SHA, а не только ревизии workflow;
   закреплённые SHA/образы; полный согласованный Compose-набор/профили; ожидаемые
   значения Broker-флага у Web, Worker и ровно одного Scheduler; соответствующие
   версии кода; образы Broker/ttyd/заданий и правила доступа Gateway. Выводить
   только разрешённые параметры, не полные env/Compose-конфигурации с секретами.
   Любое расхождение должно останавливать rollout до изменений.
5. Описать точный список изменяемых сервисов и rollback. Проверить lifecycle
   Lite, активные сессии, отзыв доступа, requested start/reset/check и cleanup
   на изолированном staging. Случайное отключение Broker, второй Scheduler,
   общий `compose up`, принудительное пересоздание Gateway и массовую пересборку
   заданий не переносить. Миграции и изменения данных должны иметь отдельный
   рассмотренный план и разрешение; не запускать общий `migrate` по умолчанию.
6. Только после этих проверок заменить обязательную остановку на reviewed
   процедуру, обновив policy и негативные тесты для её контракта. Простое удаление
   guard/тестов не является включением CD. Сохранить manual-only trigger, проверку
   неизменяемой ревизии, точное подтверждение, environment approval, сериализацию
   запусков и отсутствие production-цели. Затем отдельно разрешить переменную
   `MANUAL_STAGING_DEPLOY_ENABLED=true` и выполнить первый контролируемый запуск.

Для появления Run workflow файл должен быть в default branch. Approval
environment действует только при реально настроенных protection rules:
[события workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch),
[deployment environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
Настройки GitHub в рамках этой задачи не изменялись и не проверялись в аккаунте.

## Проверки границы CI/CD

`workflow-policy` выполняется до существующего test-job. Он разбирает YAML
с запретом дублирующихся ключей, проверяет точные команды/окружения `ci.yml`,
изоляцию SQLite, отсутствие remote/deployment jobs в автоматических workflows
и обязательные ограничения заблокированного ручного шаблона. Прежние workflow
Terminal Broker/Trusted Checker сохранены; их локальные E2E на runner допустимы.
Guard предотвращает регрессии конфигурации workflow; review изменений скриптов
и настройка branch protection по-прежнему обязательны.

Локально, без Docker, SSH, Django или миграций:

```sh
python -m pip install PyYAML==6.0.2
python deploy/ci/workflow_policy.py
python -m unittest discover -s deploy/ci -p 'test_*.py' -v
```

Проверяются отказ push/PR в CD, production target, неполный SHA, неподтверждённая
ревизия, команда в пользовательском вводе, SHA вне main, remote actions/SSH,
возврат серверных миграций/Compose в CI и обход обязательной остановки.
