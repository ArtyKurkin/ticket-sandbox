# Roadmap Backend Foundation

Контракт навигации расширен задачей 9: [Roadmap Actions & Navigation](ROADMAP_ACTIONS_NAVIGATION.md). Упоминания пустых actions ниже описывают состояние до этой задачи.

Roadmap агрегирует существующие источники без второй системы адаптации. React и Trophy Room пока используют прежний прототип; этот API к ним не подключён.

## Файлы и архитектура

Созданы:

- `roadmap/__init__.py`, `roadmap/apps.py` — регистрация Django-приложения.
- `roadmap/models.py` — журнал `TrainingConfirmationEvent`.
- `roadmap/migrations/__init__.py`, `roadmap/migrations/0001_initial.py` — новая таблица, индекс и ограничения; без изменения или восстановления старых результатов.
- `roadmap/services/__init__.py`, `roadmap/services/registry.py` — фиксированные станции, независимая доступность модулей и требования v1.
- `roadmap/services/confirmations.py` — staff-only транзакционные подтверждения.
- `roadmap/services/projection.py` — read-only агрегация Sandbox, TraineeDiary, событий обучения.
- `roadmap/views.py`, `roadmap/urls.py` — session API с CSRF.
- `roadmap/tests/__init__.py`, `roadmap/tests/test_roadmap.py` — модели, API, доказательства и конкурентные действия.
- `roadmap/examples/new_hire.json`, `roadmap/examples/internal_transfer.json` — полные ответы API для синтетических стажёров, включая все восемь станций.
- `ROADMAP_BACKEND_FOUNDATION.md` — контракт, правила, проверки и ограничения.

Изменены только `config/settings.py` (приложение) и `config/urls.py` (API). Существующие механизмы Sandbox, TraineeDiary, frontend и production-конфигурация не изменены.

## Статусы

`availability`, `applicable` и `state` — независимые поля. `display_status` задаёт приоритет: `coming_soon`, `not_required`, затем индивидуальный статус. Неприменимая станция имеет `state=null`, а не `completed`. Рабочие URL и награды не подставляются.

| № | Станция | Правило |
|---|---|---|
| 01 | training | Последнее событие `confirmed` означает completed; `revoked` снимает подтверждение. Без события обучение available, при текущем учебном этапе in_progress. Исторические переходы Teachbase не заменяют отдельное подтверждение. Для внутреннего перевода not_required. |
| 02 | sandbox | Только `SandboxQueueProgress.is_completed`, основанный на сохранённом SandboxProgramCompletion, означает completed. Текущий этап Sandbox или технические зачёты означают in_progress; подтверждённое обучение открывает available. Для внутреннего перевода not_required. |
| 03 | escalation | coming_soon, null, описание будущего модуля, COMING SOON, actions=[]; не входит в требования v1. |
| 04 | ticket_analysis | Аналогично 03; доступность задаётся собственной записью реестра. |
| 05 | with_review | Достоверный переход наставника из последнего посещения with-review в optional-review означает completed. Реальный текущий этап означает in_progress независимо от пропущенных начальных подтверждений. Для внутреннего перевода или после завершения Sandbox доступен первый рабочий этап. |
| 06 | optional_review | Аналогично, штатный следующий этап — no-review. Подтверждённый 05 открывает available. |
| 07 | no_review | Последовательный переход в done засчитывается только при подтверждённом успешном исходе ИС. Подтверждённый 06 открывает available. |
| 08 | probation | Completed только при success в существующих полях завершения ИС: финальный этап, дата в допустимых границах, дата начала финального этапа совпадает с датой завершения, автор присутствует. Пока адаптация продолжается — in_progress; terminated и недостаточный исторический результат не дают успешного завершения. |

Процент: число completed среди enabled и applicable / число enabled и applicable, округление до одного десятичного знака. Внешний найм: знаменатель 6; внутренний перевод: 4. `exempt_count=0`: освобождения как отдельный механизм не реализованы. Временной процент `journey.progress_percent` возвращается отдельно в `adaptation_progress_percent` и не используется как доказательство завершений.

Без TraineeJourney возвращаются восемь станций, journey.state=not_started, null тип/схема, 0/0 и 0%, временной процент null. Нет демонстрационных значений и достижений.

## История и legacy

История упорядочена по started_at и PK: несколько штатных переходов в один день допустимы. Для зачёта проверяется непрерывность границ посещений, допустимость этапов для схемы/типа входа, даты и согласованность единственной открытой последней записи с текущим этапом. При нарушении рабочие завершения не засчитываются, текущая позиция сохраняется, возвращается `data_quality`.

Автор следующей записи StageHistory — автор перехода, а не автор завершённого посещения. Требуется `is_staff=True`. Пропуск, нештатный переход, отсутствующий автор и выход на done без успешного ИС не дают зачёта. Последнее посещение имеет приоритет: возврат в этап снимает доказательство его предыдущего завершения, новое штатное прохождение может дать новое доказательство. Завершения остальных станций не придумываются из порядкового номера текущего этапа.

Поддерживаются legacy и unified через существующий stage_applies. Legacy не обязан иметь training-program; исторический учебный этап отображается в реальной позиции journey.current_stage, но не получает подтверждения задним числом. Недостаточные данные объясняются evidence/data_quality. История не переписывается.

## Sandbox

Расчёт полностью принадлежит `sandbox/services/progress.py`. `progress.scope=current_catalog` описывает текущие задания; `completion` отдельно содержит ID, дату и состав сохранённого результата. После изменения каталога состояние completed сохраняется, даже если текущий прогресс стал 1/2 или очередь выключена. Пример 15/15 возвращается, когда это фактический текущий каталог, а не константа.

Независимые неблокирующие уведомления: text_revision_required, text_waiting_for_review, text_answer_not_submitted, unread_mentor_feedback. Счётчики относятся к текущим обязательным заданиям и зачётным попыткам согласно контракту Sandbox; доработки не отменяют снимок и не блокируют доступность рабочего этапа.

`status=passed` и тренировочные попытки не заменяют техническое доказательство или снимок. Полное выполнение текущего каталога без снимка также не означает completed. GET ничего не восстанавливает. Legacy-восстановление выполняется существующей отдельной командой `restore_sandbox_completions` с её dry-run/fingerprint правилами, а не этим API.

## Подтверждения и аудит

Журнал хранит journey, stage_code, action, actor, created_at и comment. Отзыв добавляет событие и сохраняет прошлое. Повтор того же состояния возвращает changed=false, без новой записи. Повторный revoke до первого подтверждения — тоже no-op, event_id=null.

Сервис проверяет staff, открывает atomic и блокирует существующую строку TraineeJourney через select_for_update, затем читает последнее событие и при необходимости добавляет новое. Так сериализуются в том числе первые конкурентные подтверждения разных наставников. На SQLite нет row locks: конфликт блокировки возвращается как повторяемый 409, сильная конкурентная гарантия проверяется на PostgreSQL.

Instance save/delete и ORM update/delete/bulk_update/bulk_create для журнала закрыты. FK PROTECT сохраняют автора и адаптацию. Привилегированный SQL и внутренние ORM обходы не защищены DB-trigger: исправление/удаление аудита требует отдельного процесса. Новая таблица не хранит копию текущего этапа и не содержит назначений наставников.

Будущий автоматический провайдер обучения подключается через доверенный серверный adapter вместо manual. Коды станции, URL, state и внешний контракт сохраняются, source изменится на course; перед этим потребуется определить идемпотентный идентификатор событий курса. Клиент не может выбирать источник: POST принимает только comment.

## API

- GET `/api/roadmap/me/` — только собственная адаптация авторизованного пользователя.
- GET `/api/roadmap/trainees/<journey_id>/` — любой staff может читать любую адаптацию.
- POST `/api/roadmap/trainees/<journey_id>/stages/training/confirm/` — staff, JSON `{ "comment": "Teachbase проверен" }`.
- POST `/api/roadmap/trainees/<journey_id>/stages/training/revoke/` — аналогично, новый аудит отмены.

Ответ POST: `{ "stage": "training", "confirmed": true, "changed": true, "event_id": 1 }`. Данные entry_type/source/actor из клиента не принимаются. Комментарий необязателен, до 10000 символов. Session authentication, штатная CsrfViewMiddleware, Content-Type application/json. 400 — некорректное тело, 401 — нет сессии, 403 — нет staff или CSRF, 404 — неизвестная адаптация, 409 — обучение неприменимо либо повторяемый конкурентный конфликт, 405 — неверный метод. Ошибки CSRF возвращаются стандартным Django-обработчиком (HTML), остальные ошибки API — JSON. Успешные ответы имеют private, no-store.

Метрики сериализуются из WeeklyMetric: скорость в тикетах/час, качество, номер и начало недели; Decimal в JSON — строка для сохранения точности. Показывается fixed_quality_percent. Даты посещений и длительности возвращаются на рабочих станциях. Readiness только текущего рабочего этапа берётся из существующего сервиса, без новых порогов. Общее количество обработанных тикетов неизвестно и не возвращается.

## Включение будущих модулей

Доступность каждой станции задаётся серверным реестром MODULES. Сейчас 03 и 04 coming_soon. Набор REQUIREMENTS_V1 фиксирован независимо от доступности: изменение доступности не расширяет знаменатель старого Roadmap.

Перед реальным включением добавить requirements_version к адаптации/минимальной Roadmap enrollment, присвоить существующим v1, новым v2 и выбирать фиксированные наборы требований по версии. Модули включаются независимо; старые адаптации остаются на v1, смена требований — отдельное явное действие. Сейчас новые модули не входят ни в одну адаптацию, поэтому отдельная enrollment-таблица преждевременна. Автоматическое изменение REQUIREMENTS_V1 запрещено контрактом.

## Подключение React следующим заданием

Использовать me для стажёра, staff endpoint для карточки наставника. Маппинг по стабильному id, а не PK/order дневника. Приоритет display_status и null state сохраняют различие COMING SOON/not_required/locked. Общий и временной процент отображлять отдельно. Уведомления Sandbox не перекрашивают completed и не блокируют переходы. Рабочие действия настраивать по реально существующим маршрутам; для 03/04 только информационные карточки. POST подтверждений использует cookie-сессию и X-CSRFToken. Трофеи не вычислять из not_required: backend достижений отсутствует.
